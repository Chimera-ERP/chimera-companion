# UI/UX requirements

Status: current. Owner: maintainers of the affected interfaces.
Canonical source: ERP `docs/ui-ux-conventions.md`. The `.quality` copies in sibling
repositories are generated by ERP's `quality:sync`, not edited independently.
These requirements apply to new interfaces and changes within an existing task's
scope. They do not authorize an unrelated redesign or claim that historical
screens have already passed an audit.

## Required references and decision process

Use [Laws of UX](https://lawsofux.com/llms.txt), by Jon Yablonski, and the local
[Flawless UI/UX skill](../.agents/skills/flawless-ui-ux/SKILL.md) for interface work.
The skill and its references are pinned to the upstream revision recorded in
`.agents/skills/flawless-ui-ux/upstream.json`; its MIT license is retained.
The upstream project is [smokeeaasd/flawless-ui-ux](https://github.com/smokeeaasd/flawless-ui-ux).

Before implementation, identify the user's task, the information needed to do it,
the primary action, input mode and reusable components. Read the skill entry point
and only the references needed for the decision. Consult the relevant Laws of UX;
do not load every reference for a small change. A short rationale belongs in the
existing task checklist or review, not a new design document per conversation.

Apply principles to the actual task:

| Principle | Chimera requirement |
| --- | --- |
| [Jakob's Law](https://lawsofux.com/jakobs-law/) | Reuse established navigation and control behavior. Fix the shared primitive when the defect is shared. |
| [Hick's Law](https://lawsofux.com/hicks-law/) and [choice overload](https://lawsofux.com/choice-overload/) | Show relevant choices; progressively disclose advanced/optional fields. Use searchable, bounded entity selection for large catalogues. |
| [Proximity](https://lawsofux.com/law-of-proximity/) and [similarity](https://lawsofux.com/law-of-similarity/) | Keep labels, controls and errors together. Group through spacing and alignment; avoid decorative nested containers. |
| [Fitts's Law](https://lawsofux.com/fittss-law/) | Keep actions reachable, adequately sized and consistently aligned for the actual input device. |
| [Cognitive load](https://lawsofux.com/cognitive-load/) and [working memory](https://lawsofux.com/working-memory/) | Keep units, state, context and consequences visible. Preserve drafts and selections rather than making users remember and re-enter them. |
| [Doherty Threshold](https://lawsofux.com/doherty-threshold/) | Give prompt, truthful feedback; pending work must not appear frozen or already completed. |

These are design heuristics, not numerical pass/fail guarantees. Do not impose a
universal seven-item limit, promise sub-400 ms network operations, or relax security
and business validation in the name of permissive inputs. Existing product rules,
authorization, accessibility needs and explicit user choices remain constraints.

Laws of UX is consulted and attributed, not vendored: its site content uses
[CC BY-NC-ND 4.0](https://lawsofux.com/info/). Do not copy its illustrations or
articles into the commercial product. The requirements here are project-specific
applications, not a redistributed translation of that site.

## Composition and reusable components

Use `PageLayout` for width and rhythm, `PageHeader` for one primary page heading,
and `PageBack` before the title for contextual return. Reuse the existing `list`,
`document`, `form` and `workspace` variants rather than adding another shell.
Preserve list filters, selection and navigation context on return.

- **List:** creation belongs in the header; the registry uses `PageSurface` and
  the shared table/filter/pagination primitives below. Identifiers use
  `ListItemLink`; row actions remain independently reachable. A direct action
  must open the promised view, not an unrelated parent list. Loading, empty,
  filtered-no-results and error states retain useful controls.
- **Document:** header contains identity, date, status and relevant actions;
  sections contain parties, location, notes, deadlines and totals. Reuse
  `DocumentConfirmAction` for consequential transitions; the page owns its
  permissions, mutation and feedback. Do not repeat totals or payment methods
  without a distinct purpose.
- **Form:** use the existing shadcn `Field`/`FieldLabel` or react-hook-form
  `FormItem`, consistent spacing and a responsive grid. Every field has a visible,
  associated label, including when table headings disappear on mobile. Complex
  shadcn controls receive `disabled` explicitly even inside a disabled fieldset.
  Errors belong near the field and important failures are announced. Optional
  help does not become a permanent wall of explanation.
- **Wizard:** reuse `FormWizard` where steps reflect dependencies or volume.
  Use one progress/navigation system. The page owns step validation and state;
  do not collapse distinct business rules into an assortment of flags. Preserve
  entered values when navigating back or when a request fails.
- **Dialog/sheet/drawer:** one title and description, simple field/result groups,
  bounded height and internal scrolling. No decorative cards inside the overlay,
  including equivalent styled divs or child components. Inspect actual rendered
  children/portals; `PageSurfaceContext` is not permission to nest surfaces.
  Use full pages for sustained work and the established mobile drawer behavior.

Use one clear primary action. Icon-only controls need accessible names, centered
icons and reachable tooltips; essential meaning must not depend on hover. Preserve
concise EN/RO copy and test long labels. Status needs a label or shape as well as
color. A disabled action must expose the reason and recovery when not self-evident.
Destructive or consequential actions reuse the project's confirmation components;
pending financial/stock work cannot be retried as a new operation.

## Registry filters and selection

`RegistrySearch`, `SortableTableHead`, `ListPagination` and `useRegistryList`
compose registries whose endpoints return a **complete collection**. Filter and
sort before page slicing. Preserve unrelated URL parameters. Do not sort one
server page and present it as whole-dataset sorting; remote registries use the
existing server-side contracts. Do not add fake pagination to an incomplete array.

Use `RegistrySearch` for filter toolbars. It owns search/reset, one non-wrapping
row and the width-aware secondary filter popover. Account for the open sidebar;
no page-specific second filter row. `actions` holds table actions such as column
visibility. `ListToolbar` is for document headings/actions, not new filters.

Use the existing entity picker modal/table when selecting products or large
registries: searchable, sortable, paginated results, with the selected state and
scope apparent. Reuse `EntityTablePicker` where that workflow is already used.
`EntityPicker` is appropriate for bounded loaded location/role/channel registries;
`AsyncEntityPicker` provides debounced server search with a two-character minimum,
pagination and retry for large catalogues. Pending queries must not leave stale results selectable.
Keep organization-scoped query keys and use authorized domain endpoints.
Do not render 50 locations as a long checkbox wall or an unsearchable dropdown.

Use `DateRangePicker` (shadcn Calendar/Popover), not two independent native date
inputs. `RegistryTable.date` and the explicit date selector in `useRegistryList`
filter before totals/pagination; scoped URL date state is independent between
registries, and reset clears the period. Include
undated rows without a period and exclude them when a period is active. Document
dates use their ISO calendar date; timestamps retain the established UTC-date
convention rather than silently becoming location-specific fiscal days.

For remote registries, enable dates in `useServerRegistry` only when supported by
the API. `registryPage` validates/binds inclusive bounds against a trusted date
column and filters before COUNT/LIMIT; unsupported filters must not be ignored.
Audit, execution history, sales, physical inventories, supplier incidents,
purchase allocations, replenishment, automation runs, shifts and deliveries use
remote filtering. Fidelity reuses `registryDateBounds`: scan date for claims and
creation date for accounts, transactions, rewards and coupons.
Preserve the legacy response when the registry page parameter is absent. Use the
record's relevant date: issue, receipt, payment, operation, expiry or update.
Current stock, product/supplier/role catalogues, recipes and document lines do not
need an arbitrary date filter. Current stock is not an as-of inventory report.
Bounded diagnostics must not pretend to provide complete-history filtering.

`DocumentTotals` owns consistent spacing, not tax or currency calculations.
Supplier contacts reuse the procurement/shared contact registry; automations must
not introduce a separate recipient store. Template previews use synthetic data
and the existing PDF renderer, with an open/download fallback; a mocked renderer
is not evidence of PDF layout.

## Responsive, input and interaction acceptance

Recompose narrow screens; do not merely shrink desktop controls. Keep labels,
units, primary actions and errors visible. Use local scrolling for genuinely
two-dimensional tables, not horizontal scrolling of the entire page. Verify
icon centering, text wrapping, sticky headers/footers and overlay boundaries.

ERP density, POS touch operation and KDS industrial keyboards are distinct
contexts. POS controls retain the project's minimum 44px touch targets, fullscreen
checkout and bounded overlay scrolling. KDS paths must work with their configured
keys and cannot require a QWERTY search as their only navigation. Native Flutter
interfaces reuse their existing widgets and accessibility mechanisms; the web
skill's design principles apply, but a DOM scan cannot validate Android behavior.

Check keyboard activation, visible focus, reading order, modal focus containment,
Escape and focus return. Check contrast against actual backgrounds, supported
themes, reduced motion, zoom/reflow and text scale where affected. Loading is
truthful; a success message means the operation completed. Keep distinct states
for missing data, zero, pending, rejected and unknown outcomes.

Query keys include the organization; AppLayout remounts on organization change.
Refetch must not overwrite dirty fields. Contact drafts use scoped sessionStorage
and beforeunload protection. SMTP, WhatsApp and eFactura drafts remain in memory
scoped to user/organization/integration and clear on save or session change;
passwords are not persisted. Do not generalize these guarantees to untested forms.

## Required verification and evidence

Before delivering an interface change, perform the skill's
[final pattern pass](../.agents/skills/flawless-ui-ux/references/anti-slop.md#final-pass)
and inspect the actual primary user path, not only an isolated component.
Cover relevant loading, empty, error/retry, success, open overlay and narrow/wide
states. Inspect copy/icons in source as well as rendered alignment, spacing and
hierarchy. Use synthetic data and redact evidence; never put production screenshots
or credentials in Git.

Record the reused components, applicable principles/decisions, actual viewport and
input coverage, findings, fixes and remaining limits in the existing checklist or
structured quality receipt. No new per-task UI report is required. For a small
change, a short focused record is enough. Recheck affected states after a fix;
do not run the whole application suite for every visual adjustment.

Optional executable inspection uses the reviewed CLI version, without a runtime
application dependency or global installation:

```sh
npx --yes flawless-ui-ux@1.0.0 inspect --project . --source src/App.tsx --url http://localhost:5174 --output .quality-receipts/ui-example --format json
npx --yes flawless-ui-ux@1.0.0 verify .quality-receipts/ui-example/run.json --output .quality-receipts/ui-example-after --format json
```

Use the actual changed source, running URL and fresh output directories. Prepare
a compatible browser separately when needed. Read
[inspection coverage](../.agents/skills/flawless-ui-ux/references/inspection.md):
source/initial-state scans are supplementary, not complete accessibility,
keyboard, business-flow or visual acceptance. Report unavailable rendering and
unexecuted checks explicitly. A successful CLI exit does not mean the design is good.

`quality:check` verifies generated contract/reference consistency and integrity;
it does not prove that a person/agent followed the review or that every screen
meets these requirements. Human review and real interaction evidence remain needed.
Run ERP's `quality:sync` after approved canonical changes. Updating the vendored
skill requires review of the upstream diff/license and refreshed provenance/hashes;
never silently track `latest` or overwrite local edits through an installer.
